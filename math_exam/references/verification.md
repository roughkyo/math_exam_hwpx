# 수식·내용·지면 교차검증

## 수식 작성 규칙

| 원문 요소 | 한글 수식 예 | 필수 확인 |
|---|---|---|
| 음수 분수 지수 | `3^{-{1} over {2}}` | 음수가 지수 안에 있는지 |
| 선분 길이 | `bar {rm {AB}}=5` | 윗줄과 =5, 다른 행의 C₂ 혼입 여부 |
| 첨자 | `C_{1}` / `C_{2}` | 각각 독립된 기호인지 |
| 함수명 정체와 간격 | `sin x`, `ln 2`, `log _{5} 3` | 한글 내장 함수명 사용, 강제 ~ 일괄 삽입 금지 |
| 분수·합·극한의 큰 괄호 | `LEFT ( {1} over {27} RIGHT )^{x}` | LEFT/RIGHT 명령, 내용 높이에 맞는 괄호 |
| 수식 안 쉼표 | `(a, b, c)` | 본문 쉼표와 구별하고 원본의 간격 유지 |
| 조건부확률 | `{rm {P}} it (B~|~A)` | 세로선과 양쪽 기호 간격 |
| 한글 조건 | 보통 문단의 수식 X + 텍스트 `가 0 또는 1의 값을 가지는 경우` | 한글은 hp:t, 조건 전체를 수식화하지 않음 |
| 벡터 절댓값 | `LEFT | vec {rm {AX}} RIGHT |` | 벡터 화살표·괄호 높이·기준선 |

쉼표·괄호가 본문에 있으면 별도의 본문 개체를 그대로 유지한다. `A`, 본문 `, `, `B` 순서다. 수식 내부 수열의 쉼표는 의미를 보존하고 간격을 확인한다. 괄호/인용 구문의 균형 검사는 전체 의미 검증을 대신하지 못한다.

조건별 함수는 각 행의 값과 수학 조건을 별도 수식으로 배치하고 한글 조건은 일반 텍스트로 작성한다. 같은 조건 안에서도 수학 기호와 본문을 보통 문단의 인라인 개체로 나눈다. 가운데 0, 오른쪽 정렬 f(x), 조건 열의 시작 위치를 유지한다. 필요하면 중괄호를 별도 한글 수식으로 만들되 행 수에 맞춘 높이를 실제 한글 출력에서 조정한다. `cases` 문자열을 넣었다는 이유로 행/열 간격이 보존됐다고 간주하지 않는다.

## 필수 검증 순서

1. 원문/출제 원고와 본문·수식의 순서를 비교한다. 문항 번호, 조건, 선택지, 배점, 홀수형, 저작권, 확인 사항을 쪽별로 점검한다. 문자 집합 비교만으로 통과시키지 않는다.
2. `validate_exam.py`로 ZIP·수식·그림·배점과 수식 높이 경고를 검사한다. 미검토 경고를 모두 확인한다. 원문과 배점 값/개수를 쪽별로 비교하며, 일치하더라도 배점 위치가 같은 문항 뒤인지 눈으로 확인한다.
3. Windows 한글이 있으면 `render_hancom.py` 또는 실제 UI에서 새 파일로 저장·PDF 출력한다. COM 실패 시 생성된 파일의 ZIP/쪽 수를 확인한다. 완료되지 않은 PDF를 덮어쓰지 말고 저장된 HWPX를 새 한글 인스턴스에서 다시 열어 새 이름의 PDF로 출력한다. 자기 작업에서 만든 숨은 인스턴스 외 다른 한글 창을 종료하지 않는다.
4. 전체 쪽을 축소 지면으로 확인하고 문제가 있는 부분을 확대한다. 수식별 source_bbox를 기록한 검증 spec으로 픽셀 비교한다. 낮은 점수뿐 아니라 지수·분수·윗줄·한글 조건·쉼표·cases·수정 위치는 필수 확대 확인한다.
5. 보고서의 수정 주장 각각을 최종 출력본에서 재확인한다. 자동 검사 결과의 `visual_verified:false`는 사람이 실제 출력물을 확인한 별도 기록을 썼을 때만 완료 판단에 사용할 수 있다. 스크립트가 이를 자동 true로 바꾸지 않는다.

검증 spec:

```json
{
  "threshold":0.35,
  "regions":[{"source_page":1,"output_page":1,"bbox":[60,220,210,275],"label":"1번 수식"}],
  "pages":[{"source_page":1,"output_page":1,"required_text":["홀수형","저작권"]}]
}
```

```text
python scripts/validate_exam.py output.hwpx work/새검증폴더 --source-pdf original.pdf --output-pdf rendered.pdf --spec regions.json
```

비교 점수는 검은 픽셀의 상호 포함률이며 2배 렌더링에서 1픽셀의 위치 여유를 준다. 낮은 점수는 글꼴/조판 차이일 수도 있다. 높은 점수도 내용 정확성을 보장하지 않는다. 2025처럼 양식과 PDF의 배치가 다르면 해당 수식의 개별 위치를 맞춰 비교하거나 기존 수식 스크립트 동일 여부와 별도 육안 검증을 기록한다.

원본이 없는 새 출제는 예시 PDF의 모양 비교로 수학적 정답을 검증하지 않는다. 독립 계산과 문항-그림-해설 일치 검사가 필요하다. 한글이 없으면 “구조 검증 완료, 실제 한글 출력 미검증”으로 보고한다. LibreOffice 등의 미지원 렌더러 결과를 한글 검증으로 대체하지 않는다.

## 1.1 실제 조판 검사

검토가 끝난 수식 블록에 `source_script`를 기록한다. 원본을 별도로 보존하며 재구성 과정에서 이 값을 출력 스크립트로 덮어쓰지 않는다. `stretch_parentheses_required`는 새 출제에서도 분수·합·극한 등을 감싼 자동 높이 괄호에 지정한다. `--plan`은 조립 후에도 원고 순서와 괄호 정보를 검사한다. 일반 괄호와 큰 괄호를 같은 문자열로 정규화한 결과는 내용 확인용일 뿐 조판 보존의 증거로 쓰지 않는다.

`--layout-spec`은 실제 출력 PDF 좌표(pt)를 사용한다. 원본 PDF 좌표와 HWPX의 머리말 내부 좌표를 그대로 대입하지 않는다. 각 쪽의 바닥글이 한 행 안에 완전히 있는지, 홀수형 글자가 머리말 안전 영역 안에 있는지, 본문과 겹치는지, 지정된 색상인지 검사한다. 실패는 종료 코드 1이다.

```json
{"layout_checks":[
  {"page":1,"text":"홀수형","region":[80,45,780,100],"max_lines":1,"no_body_overlap":true,"body_top":110},
  {"page":1,"text":"이 문제지에 관한 저작권은 한국교육과정평가원에 있습니다.","region":[450,1090,820,1140],"max_lines":1,"colors":[255]}
]}
```

위 좌표는 한 출력 양식의 예시다. 다른 양식/첫 쪽에는 실제 위치에 맞춘 영역을 만든다. 색상 255는 RGB 파랑이다. PDF에서 글자를 찾지 못하면 검증 실패로 남기고 육안으로 확인한다. 글자의 상자 위치 검사는 테두리 유무, 실제 굵기, 분수·지수의 모양을 보증하지 않으므로 해당 부분은 확대 확인한다.

기준선·행 높이·열 정렬의 다른 표현을 포함하는 한글 수식 문법에서는 중괄호 개수만으로 오류를 단정하지 않는다. `LEFT{ ... RIGHT.` 같은 편측 중괄호는 정상 조판일 수 있으며 원문과 출력 대조로 판단한다. `흰 공 1개`, `도형을 T라` 같은 경계는 원고 공백뿐 아니라 실제 출력의 앞 글자 끝/수식 시작 위치를 확인한다. 간격 변경 후 바로 뒤 본문을 침범하지 않는지도 확인한다.

## 1.2 직접 편집과 경계 검사

수식 글꼴, baseUnit, 실제 폭·높이·기준선을 한글 엔진으로 측정한다. 스크립트의 보이는 길이를 문자 수로 추정해 후속 본문을 배치하지 않는다. 다른 글꼴로 측정한 치수를 쓰지 않는다. 조립 → 한글 열기 → 저장 → PDF 출력 → 다시 열기의 순서로 검사한다.

본문 편집 시험: 복사본에서 본문 단어를 한글 찾기로 선택하고 InsertText로 같은 길이 또는 다른 길이의 보통 텍스트로 바꾼다. 저장한 HWPX의 본문 변경과 전체 수식 스크립트 불변을 확인한다. 수식은 hp:equation으로 남고 텍스트만 바뀌어야 한다.

확대 점검 항목: tan θ의, cos θ의, sin θ+3cos θ=0이고, 적분 dx의, Q(log₅ 12)에, (a,b,c,d)의, 좌표 뒤 조사, log₉ ab의, ln 2/ln 3, |sin x|cos x, 흰 공 1개. 원고에 띄어쓰기를 넣었다는 기록만으로 통과시키지 않는다. 한 셀 문단의 의도치 않은 추가 줄, 글자 겹침, 열 경계 침범, 다음 문항과의 충돌을 확인한다.
